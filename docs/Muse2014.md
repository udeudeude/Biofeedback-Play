# Muse 2014 / MU-01 integration

Biofeedback Play targets the first-generation InteraXon Muse, model MU-01.

## What is different about this Muse

MU-01 is not the Bluetooth Low Energy Muse used by most current Muse examples. It uses classic Bluetooth RFCOMM, effectively a Bluetooth serial link. Projects written for Muse 2016, Muse 2, or Muse S generally use a different transport and should not be treated as drop-in references.

A particularly useful current reference is Matthew Piercey's open-source **muse-2014-lsl** project:

- https://github.com/mtpiercey/muse-2014-lsl
- specifically targets Muse 2014 / MU-01
- updated in 2026
- MIT licensed
- uses RFCOMM and preset AD
- decodes EEG, accelerometer, and battery packets
- documents that the 2014 model normally appears with a name such as `Muse-A1234`
- notes that pairing may be needed before opening the RFCOMM connection

Biofeedback Play's parser and connection sequence are intentionally cross-checked against this implementation rather than against modern BLE Muse libraries.

## macOS connection strategy

Biofeedback Play now supports two macOS paths:

1. direct access to the paired classic-Bluetooth device through Apple's IOBluetooth RFCOMM API
2. a classic serial endpoint such as `/dev/tty.Muse-...` or `/dev/cu.Muse-...` as a fallback

Native RFCOMM is tried first. A real-world trace showed that macOS could expose `/dev/tty.Muse-A620` and `/dev/cu.Muse-A620` endpoints that opened without errors but returned zero bytes and consumed the entire connection budget. The same attempt then discovered two real RFCOMM candidates only after the deadline had already expired. Prioritizing native RFCOMM avoids that dead-end.

The second path matters because modern macOS may know about the paired headset without creating a useful `/dev/cu.*` device. The Device setup page therefore lists both serial endpoints and paired classic-Bluetooth devices.

The paired-device list is deliberately not filtered to names containing `Muse`. During earlier testing this user's headset appeared in macOS as **Watch**, so an unexpected generic name must remain selectable. Direct paired-device selections are stored as `bt://<Bluetooth address>`, which lets Biofeedback Play target that exact device even if its displayed name is unhelpful.

Bluetooth Settings is useful for seeing or pairing the headset, but macOS's transient “Connected” state is not used as proof that Muse data is available. Biofeedback Play considers the Muse live only after actual Muse packets arrive.

## Connection diagnostics

Each connection attempt now keeps a short trace. It records:

- connection stages
- serial endpoint attempts
- RFCOMM channel candidates
- whether CRLF or CR command termination is being tried
- commands sent to the headset
- short textual responses from the headset
- failures from individual transport attempts
- the passive pre-command stream probe

The trace is visible in Device setup and can be copied directly. This should make a future failure distinguishable as, for example:

- no usable paired device
- no serial endpoint
- baseband connection failure
- RFCOMM channel open failure
- RFCOMM open succeeded but version handshake failed
- commands succeeded but no Muse packets arrived

The app performs one bounded diagnostic pass rather than retrying forever.

## Command framing

The 2026 muse-2014-lsl implementation sends Muse serial commands with CRLF line endings. Biofeedback Play now tries CRLF first, then CR as a compatibility fallback.

The connection sequence is based on the archived InteraXon protocol documentation and the working open-source implementation:

- `h` stop an existing stream
- `v 2` protocol/version query
- `r 4` platform = Mac
- `% AD` research preset
- `?` status query
- `s` start streaming
- `k` keepalive every five seconds

The external muse-2014-lsl implementation does not require a separate `s` command in its tested Linux flow, while older Muse documentation and implementations use explicit stream control. Biofeedback Play keeps the explicit start command for now but exposes enough connection trace to tell us exactly how this particular MU-01 responds next time it is available.

## Streaming protocol

Preset AD contains the packet forms currently supported by Biofeedback Play:

- `E0` + 8 bytes: four-channel uncompressed EEG
- `A0` + 4 bytes: accelerometer
- `B0` + 8 bytes: battery
- `FF FF AA 55`: synchronization marker

The EEG channels are exposed as TP9, FP1, FP2, and TP10. Preset AD is treated as 500 Hz EEG and 50 Hz accelerometer based on the referenced implementation.

## Scaling cautions

The microvolt conversion uses the same AFE-gain-based approach described by the open-source clean-room implementation. Its author explicitly notes uncertainty around the exact scaling. Biofeedback Play therefore labels these values as experimental microvolts rather than calibrated EEG measurements.

Accelerometer channels are currently kept as signed raw 10-bit values instead of applying an uncertain physical-unit conversion.

## Useful external resources

- Muse 2014 LSL: https://github.com/mtpiercey/muse-2014-lsl
- Lab Streaming Layer supported-devices documentation lists MU-01 separately from later Muse generations
- XvMuse: https://github.com/jasonjsnell/XvMuse documents testing with Muse 1 (2014) as well as newer models, though its transport layer is not the same code path Biofeedback Play uses
- muse-lsl: https://github.com/alexandrebarachant/muse-lsl is valuable for later Muse models but explicitly targets the 2016/classic BLE generation rather than MU-01

The important rule for future debugging is to verify that a reference actually targets **MU-01 / Muse 2014** before borrowing its Bluetooth instructions.
